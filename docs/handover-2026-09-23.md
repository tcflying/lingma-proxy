## 2. 复盘：09-18 → 09-22 干了什么（按轮次）

### 第一阶段：救活（09-18 ~ 09-19，原会话）

- **诊断**：新版 Qoder CN 推理网关只认客户端内 WASM `prepareRequest` 签名，Go 侧重放
  一律 403/503；旧 cosy 凭据不再落盘。结论：**任何"Go 里重放网关请求"都是死路**。
- **方案**：新增 `qodercli` 后端（`internal/qodercli/`）——spawn 桌面版自带 CLI/worker
  runtime 子进程，签名交给客户端自己。凭据链全本地：DPAPI 解 `Local State` →
  `auth.v1.dat` device token → `/api/v1/me/jobToken` → 注入子进程环境变量。
- 推到私有仓库 `tcflying/lingma-proxy`；四家客户端（ZCode / MiniMax Code /
  opencodex(Codex) / DSH）接入。
- **档位体系定稿**（反复推翻两次才钉死）：档位是**每个模型一套**，不是全局梯子；
  Qwen3.8-Flash 实际只有 `none/low/medium/xhigh`；**不传档 ≠ 关思考**（比 xhigh 更费）。
- 拆成三个单二进制变体：`cn`(8095) / `intl`(9095) / `both`(10095)，同一份代码零分支，
  由打包脚本注入站点配置。

### 第二阶段：稳定性（09-20）

- 鉴权握手网络抖动被报成裸 500（客户端判不可重试）→ `ErrTransientUpstream` 哨兵 →
  可重试 503；端口收敛为**本机只跑 10095**。
- 历史图片把会话钉死（`requestHasImages` 扫全历史而非当前轮）+ 登录态失效时
  CLI 侧旧缓存报 `token is not active`（CN 桌面端其实还是登录态）→ 修复 + 文案。
- `/v1/models` 两站点**串行**探测 7.8s，客户端超时误判假 500 → 并行化 + 列表缓存。
- **239"黑窗闪退"真因**：服务方式启动不进交互会话，DPAPI 拿不到主密钥 →
  解法：WinRM + `Register-ScheduledTask -LogonType Interactive` 拉进 console 会话。

### 第三阶段：正确性大审查（09-21）

用户症状："别的 IDE 接代理，回复老带 tool calling，或话没说完就断"。派子代理全局
审查 + 翻代理实盘流量，实锤三条根因并全部落地（`b835420` + `1e108da`）：

1. **过滤器和解析器两套标准**（两症状共同来源）：流式过滤器认为"块开始"的标准比
   解析器宽，且 `blocked` 永久吞增量。修法：抽 `matchActionBlock` 唯一判定，
   过滤器改状态机（块前散文照流、块按字节区间丢、块后继续、未闭合当散文放回）。
   **铁律：以后动解析器必须同时动过滤器，两边共用同一把尺子。**
2. **被杀/取消的 CLI 子进程被当成功**（半句话 + HTTP 200）：只有见过 `result` 帧
   才允许在非零退出下报成功。
3. **假流式**：整轮只在结束时 emit 一个 delta，首字 51.3s。加 `--print
   --include-partial-messages` 拿真增量（首字 10.2s）+ 正文前每 15s 一个 SSE ping。
4. **XML 方言工具调用**（ZCode 实测头号主因：库里 200 处 vs 代理自有围栏 1 处）：
   `scanXMLBlock` 手写解析，两种方言统一校验，参数按 schema 回正类型，半截标签不漏。
5. 顺带：qodercli 支持**图片输入**（`userFrame` image block，只保留当前轮附件）；
   `finish_reason` 改读 result 帧真实 `stop_reason`（6 处硬编码全换）。

### 第四阶段：收尾修复（09-21 深夜 ~ 09-22 早，`cb94e1f`→`370d30d`）

审查清单逐条回代码核实（**三条复查为假，不在做**：`RLock 下广播`、`error_max_turns`
（`--tools "" --max-turns 1` 下不可达）、`app.go:2198` 配置清零（每字段有非空守卫）），
真问题修掉：

- `truncateRecordedString` 空转（1.29GB RSS 主因）→ 8 KiB 截断、rune 边界。
- 每请求整份打印请求体（含图片）到 stdout → 删。
- DPAPI use-after-free（`LocalFree` 后返回值还指着那块内存）→ 先 copy 再 free。
- `tool_choice:"none"` 只挡注入没挡解析 → 两边同一开关。
- `remote.Client` 把探测结果写进共享 `c.cfg.BaseURL`（并发 chat 正读同字段）→
  可变域名收进 `base+baseMu`，探测显式传参。
- `ensureConnected` 全程持 `s.mu` 走拨号（一次慢重连冻住所有端点）→ `connectMu`
  只串行化握手，锁序 connectMu → mu。
- 桌面端"先探测再 ListenAndServe"的 TOCTOU → 绑一次直接 `Serve(ln)`。

### 第五阶段：Web 控制台（09-22 15:2x，`1941a13`）

- 用户要"完整可写版 webui"。设计要害：**控制面不能挂在代理端口上**——
  `UpdateConfig` 内部就是 `StopProxy()+StartProxy()`，同监听会自杀。所以独立端口
  = 代理端口+1（10095→10096）。
- `desktop/control.go`：读 `/api/admin/{version,status,config,detection,models,stats,
  console,requests,requests/detail,logs,logs/detail}`，写 `POST {config,models/refresh,
  models/select,requests/clear,logs/clear,proxy/{start,stop,restart}}`，全部直调现有
  App 方法零重写。Bearer token（per-install 32hex）门禁，SSE 额外允许 `?token=`。
- `browserBridge.js`：无 `window.go` 时装同名代理转 fetch，5 个 Vue 视图一行未改。
- 同轮抓到的大 bug：**app-state 文件膨胀到 214MB**（8KiB 上限只管新记录，旧全量记录
  被无限读回写回）→ 上限挪到"往外写的关口"，214MB → 3.4MB。
- 注意：这个提交混了控制台 + 持久化上限两件事（按文件 git add，app.go 两边都沾），
  已选择不拆历史。
- 09-23 加固（同一轮补上）：控制面**默认只绑 `127.0.0.1`**，代理监听 `0.0.0.0` 时也不再
  跟着暴露——它能改配置、重启代理、读请求体，明文 HTTP + 单令牌不该默认进局域网；要放开
  得显式设 `LINGMA_CONSOLE_HOST`。令牌比对换成 `subtle.ConstantTimeCompare`。
  `ConsoleInfo` 直接报**实际绑定地址**（不再从 cfg 反推端口）。新增
  `desktop/console_test.go` 5 条：三种缺/错令牌的 401、读路由回真状态、未知端点先 401
  再 404（不让人无令牌枚举）、SSE 真收到帧、默认 loopback 与 opt-in。

## 6. 已知坑（接手前必读）

1. **Bash 里内联 PowerShell 的 `$` 会被转义吞**——写 .ps1 脚本文件执行，跑完删。
2. **`python` 解析到 LibreOffice 内嵌 python**（PATH 第一位）——显式用
   `C:/Users/Administrator/AppData/Local/Programs/Python/Python312/python.exe`。
3. **Git Bash 的 `{ ...; }` 不是子 shell**，块里 `cd` 会漏到后续命令——曾因此把
   239 共享上的 zip 意外覆盖（字节相同无损失，但属于计划外网络盘写入）。
4. **在回复正文里写出工具调用标签的字面量会被自己的解析层当真触发**——涉及
   XML/action 标签一律拼接或中文描述，不贴原文。
5. **引用实测前必须 Read 对应输出文件本身**——曾两次把别的运行结果读串当成复现。
6. **"zip 名字对上了" ≠ "里面 exe 是新的"**——校验永远回读哈希，三处（zip 内、
   Release 资产、239 落盘）都要。
7. 含口令的临时脚本用完即删，`grep -rl` 复查零残留后再收工。
8. **手工 `go build` 不重新生成 `wailsjs` 绑定**（只有 `wails build` 会）。给 App 加新方法后，
   前端要调它只能走 `window.go.main.App.X()`；写成 `import { X } from 'wailsjs/.../App.js'`
   会让 `npm run build` 直接报“未导出”，比运行时错误更早也更吵。
9. **`printf` 的格式串里别放 Go 的 `%v`**：bash 的 printf 会当格式符报错，而
   `printf ... >> file` 的重定向**在报错前就已把文件打开追加**，留下半截内容——
   本轮就据此把一段被截断的重复函数追加进了 `control.go`。要写文件用 Write/Edit。
10. **`gofmt -l .` 在这台机器上会报假脏**：检出是 CRLF（git autocrlf），gofmt 视 LF 为
    规范，于是把纯行尾差异报成"未格式化"。判断标准是 `git status` 有没有变化——
    曾据此差点提一个内容为空的 `style:` 提交。真正的门禁写法：
    `gofmt -l . ` 之后逐条对 `git diff --stat`，或直接 `gofmt -w . && git status --short`。
11. **本机 `.gitignore` 里 `cmd/lingma-ipc-proxy` 命中目录名**：`git add` 该目录下的
    `main.go` 会被 ignored 拦下并让整个 `git add` 失败（退出 1，其余文件已入暂存）。
    已跟踪的文件用 `git add -f` 即可，不是需要改 ignore。
12. **`Compress-Archive -DestinationPath x.new` 直接报错**：它只接受 `.zip` 后缀。
    想"先写在旁边、校验后再顶替"要用 `xxx-stage.zip` 这类临时名，再 `Move-Item -Force`。
13. **全量 `go test ./...` 在这台机器上会和子代理/构建抢 CPU**：包被 11 分钟默认超时杀掉并
    报 `Test killed: ran too long`，看着像死锁其实只是饿死。判绿之前先单独重跑那两个包
    （httpapi 39s、remote 52s 就过了），或给 `-timeout 25m` 并串行跑。
14. **`/health` 曾经 15–35 秒不返**：它读的后端状态与站点探测共用 `s.mu`，改成存活探针
    （不读状态）后实测 62ms 返 200。任何"探活"用途都不要碰带锁的状态接口。
    当时把持有者写成"整轮对话"是**错的**——`runPromptLocked` 全程不持 `s.mu`，
    真正的长持有者见第 17 条；只是把探针摘掉等于把病藏起来。
15. **脱敏要放在"读回内存"那一侧**：控制台令牌不再写进日志环之后，磁盘上旧的日志环仍会把
    令牌端给 `/api/admin/logs`——因为 `loadAppState` 是直接赋值。改为加载即 `trimPersistedLogs`
    （内部 `redactPlainText`），实测服务侧命中数从 2 归 0。

16. **别把 GitHub 的资产可见性延迟当成仓库坏了**（本轮最贵的一次误判，全程实录）：
    `gh release create <tag> <文件>` 当场回 201，但**接下来几分钟内**
    `releases/tags/<tag>` 与 `releases?per_page` 都回 `assets=0`、`gh release download`
    报 "no assets to download"、按数字 id `GET`/`DELETE` 回 404（`--clobber` 因此失败，
    它要先删）。我据此下结论"仓库级失同步、疑似改名遗留"，还连建两个新 tag 复现、
    把旧 release 删了重建 —— 全是围着空气在做功。
    真相反转只需要多等几分钟 + 换一条读法：`gh api repos/…/releases/tags/desktop-3site`
    稍后就列出三个资产，并带 `digest: sha256:<与本机 zip 完全相同的摘要>`（GitHub 自己算的，
    比"下载回来再哈希"更强的服务端证据），`gh release download` 也能取回且 `cmp` 全一致。
    可复用的口径三条：① 刚上传先等 ~5 分钟再判生死，别立刻下结构性结论；
    ② 私有仓库匿名 curl/WebFetch 打 `github.com` 与 `api.github.com` 一律 404 是正常隐藏，
    不是故障证据（本轮我先在这上面错了一次）；
    ③ release 资产真值优先看 API 的 `digest` 字段，再看下载回读。
17. **锁内不要碰磁盘**（239 上 `/v1/models` 与网页控制台一起 180 秒不返的真因）：
    `cliSites()` / `cliClientFor()` 曾在持有 `s.mu` 独占锁时调用 `qodercli.UsableSites()` 与
    `DetectSite()`，这条路径要做三件慢事：查注册表（`registryInstallRoots`）、对 `PATH` 上每个
    目录和各安装根做 `firstMatch` glob、扫配置目录读登录缓存（`detectProfileDir` /
    `hasAppCredential`）。同一次探针实测：`/health`（不碰锁）143ms 正常，`/v1/models`
    （`s.backend()` 要锁）和网页控制台（`svc.State()` 要锁）一起超时。
    修法是探测挪到锁外、`sync.Once` 每进程一次，锁内只发布结果；`cliClientFor` 双检发布。
    同一类问题还有一处：`resolveSession` 过去在锁内做 `session/new` 的 IPC 往返。
    **判据**：只要一个接口"该活的活着、要锁的全挂"，就是锁内有 IO，不要先去怀疑进程死了。
18. **不要把预热放在监听之前**（命令行版曾经的死法）：`svc.Warmup()` 过去在
    `ListenAndServe()` 之前跑，而 qodercli 的预热要拉起桌面运行时签 job token。
    `exec.CommandContext` 只 Kill 直接子进程，孙进程继承了输出管道，`cmd.Wait()` 还在等 EOF，
    于是 10 秒 ctx 管不住它。局域网那台实测：进程活着、CPU 0.02 秒、无监听、
    `fg.out`/`fg.err` 全空（连"listening on"都没打出来），看起来像"程序没启动"。
    改成**先开端口再预热**后，同一台机器 stderr 里两秒就出现 `listening on http://127.0.0.1:10095`。
    试过两种"更进一步"，最后都回退，理由要说准：
    ① 预热预算 10 秒 → 1 分钟；② 给目录探测加一把 `cliProbeMu`，不让预热和客户端请求重叠。
    **回退的正确理由是"没有可证明的收益 + 有隐患"**：锁的持有者自己就可能卡在 `cmd.Wait()`
    里耗尽预算，排队的调用会跟着一起超时——这是设计上的 starvation，不是实测出来的事故。
    ⚠️ 我一度把那台机器后来"`/v1/models` 连挂、对话报错"归因给这两笔改动，**A/B 回测推翻了自己**：
    把当时能答 31 个模型/220ms 的旧二进制（`1d4a3549`）原样放回去，同样 150 秒超时，
    而 stderr 显示监听正常、`C:\Users\datoo\.qoder-cn\` 的 `.cache`/`logs`/`memory` 在同期被另一个
    还在用的 Qoder 会话写动（1:41–1:49）。⇒ **变的是那台机器，不是构建**。
    教训：跨时间比较远程实测结果前，必须留一份"当时能跑"的二进制回去做 A/B，
    否则就会把环境漂移写成代码结论（本轮我错了两次）。
19. **桌面版不能指望无人值守的局域网机器**：`startup()`（绑端口、开控制台）在 Wails
    创建窗口之后才被调用。239 那台在我 `taskkill /F` 之后再也起不来，四条互相独立的信号
    都指向"卡在窗口创建之前"：进程活着但 **CPU 停在 0.02 秒**、**不派生自己的
    `msedgewebview2.exe`**（按 `--user-data-dir` 里含 `Lingma` 归属统计，own_webviews=0，
    同机另外 25 个都属于别的程序）、**app-state 的 mtime 冻在死掉那一刻**（`startup()` 会写它）、
    **10095/10096 一个都不监听**。对照：本机同一份构建活得好好的（CPU 32 秒、有窗口句柄）。
    别用 `MainWindowHandle` 判断远程会话里的 GUI——从 WinRM（session 0）读 session 1 进程的
    句柄本来就查不到，我第一次就拿它当过证据，那条不成立。
    定性：那台的交互会话当时已不适合再拉 GUI（同机另有活动 Qoder 会话在写
    `~\.qoder-cn\`），要恢复 GUI 得有人到控制台前解锁/登录。
    操作口径：局域网机器跑**无窗口构建**（`cmd/lingma-ipc-proxy` 交叉编译出的 exe，
    放同样的 `lingma-proxy.json` 在旁边即可，它只读不改这份配置），实测 stderr 两秒内
    `listening on http://127.0.0.1:10095`；**别拿硬杀当重启手段**。
20. **计划任务"Running"状态下 `Start-ScheduledTask` 是空操作**（本轮 239 上最费时间的一个
    假象）：`taskkill /F` 杀进程**不会**把任务实例置为完成，任务仍是 `Running`
    （`LastTaskResult=0x41301` = "任务正在运行"）。这时再 `Start-ScheduledTask` 直接返回、
    **不派生新进程**，看着就像"我起了进程但它不监听"。正确顺序是
    `Get-ScheduledTask … | Stop-ScheduledTask` → `taskkill`（清残留）→ `Start-ScheduledTask`，
    并且每次 `t+N` 都同时打 `pids / listeners / health` 三样，别只看 health。
    本轮我有两次把"这样启动根本没生效"误判成"起来了但不绑端口"。
21. **`service.New()` 自己也要扫磁盘，所以"绑端口"这一步在慢机器上要几十秒**：构造函数里
    `ResolveBackend(&cfg)` → `resolveRemoteBackend()` → `remote.LoadCredential("")` 扫登录缓存 +
    `qodercli.Available()` 又走一遍注册表/`PATH` glob。第 17 条把探测从锁里搬出来之后，
    这条仍在**监听之前**。239 实测：装最后的构建后 `t+10..t+40` 无监听、`t+50` 才绑上并回
    `/health` 200。升级路径就是 `cliSites()` 那一套（`sync.Once` 记结果、构造只做赋值），
    代码里已用 `ponytail:` 注释钉在 `service.New` 里，别再当成"程序启动慢"。
22. **共享局域网机上，qodercli 后端的可用性取决于"那台机器当下有没有人在用 Qoder"**：
    同机有活动会话在写 `~\.qoder-cn\`（`.cache`/`logs`/`memory` 的 mtime 与我的探针同时刻）时，
    `/v1/models` 的目录探测会 60–150 秒不返，而 `/health` 一直 200。这不是锁、也不是构建
    （A/B 过），是外部登录态被占。判据：先看 `~\.qoder-cn\` 与 `~\.qoder\` 的 mtime
    是不是在动，再决定要不要怀疑代码。
23. **变体探测的 etiquette**（本轮踩过）：那台的 `both` 是日常实例，探测 cn/intl 变体时
    只准停"自己起的那两个"，收尾必须回读 `LEFT_RUNNING` 确认 `both` 还在，且**不要用
    `Stop-Process`/`taskkill` 去停日常实例**（本轮就是这一步把后面所有事引爆的）。
    起停一律走 `Register-ScheduledTask -Principal (New-ScheduledTaskPrincipal -LogonType Interactive)`。
    实测结论：`intl` 变体在那台能起来（`/health` 200、`10096` 无令牌 401），
    `cn` 变体 150 秒内既不监听也不生成 app-state ⇒ 那台缺 CN 登录态，属机器条件不是代码缺陷。
